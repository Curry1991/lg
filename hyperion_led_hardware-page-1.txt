satdx62 07/22/2026 3:39 PM
The NV12-YUV conversion has been completely moved to HyperHDR, which
uses a LUT table for this purpose (no calculations when converting from
YUV to RGB). Using the selected LUT, the YUV to RGB conversion and tone
mapping can also be performed in one step without loss. This means that
we reduce the client load, as not only is the processor load reduced,
but no additional resources, e.g., memory, need to be allocated. You
also do not need to use external YUV libraries. Reduced load on the
connection bandwidth. The NV12 frame is around 50% smaller than the RGB
frame. This means that the automatic LUT calibration with YUV
coefficient detection can be fully utilized.

Hyperk News: Hello @everyone, As I mentioned earlier, HyperSerial has
been implemented in Hyperk test firmware version 0.0.5-alpha.1.
https://github.com/awawa-dev/Hyperk/releases I tested Hyperk’s
functionality as a HyperSerial driver specifically with HyperHDR. First,
I flashed and configured an ESP32 using the Advanced Firmware Flasher
https://awawa-dev.github.io/hyperk/installer.html Flashing an ESP32-S2
Mini only worked with esptool. The advantage of the ESP32-S2 is that it
does not require a kernel driver in LG mode, unlike other ESPs that use
CH340/341 or other serial chips. When configuring Hyperk on the ESP32-S2
Mini, the “Disable Neopixel over SPI” option had to be enabled so that
all 263 LEDs in my test environment would light up. Without this option,
only about 217 LEDs lit up. This option is intended to force the
ESP32-S2 to use RMT. To ensure that HyperSerial works (enable it first
in Hyperk), be sure to select the Adalight driver in HyperHDR:
High-speed serial AWA protocol with data integrity checking Correct baud
rate and serial port Esp8266/ESP32/RP2040/RP2350 handshake Force
HyperSerial detection Once the settings were configured and saved,
everything worked right away. And what can I say—it exceeded my
expectations. Compared to the standard HyperSerial or HyperSerialPico,
there are no drawbacks, so Hyperk can be used as a versatile LED
controller for any situation and configuration, whether via Wi-Fi or
standard serial control over USB. It’s conceivable that dual-mode
operation could be controlled via the Wi-Fi interface functions in the
future. (edited)

Hello, FCOB LEDs are completely unsuitable for Ambilight. However, due
to technical limitations, they are only partially suitable for creating
a perfect Ambilight effect. With FCOB-SPI strips, it is generally only
possible to control zones with a length of about 5 cm to 7 cm
individually. On small screens, this can result in too few addressable
areas to ensure precise color reproduction. RGBW LEDs like the
SK6812RGBW are the better solution here, since they are fully integrated
into the HyperSerialPico controller’s firmware and will give you the
best results. The Adafruit Feather RP2040 SCORPIO, on the other hand, is
a very good choice. (edited)

By the way, a good alternative to WLED is “Hyperk,” a minimalist,
powerful, and cross-platform Wi-Fi LED driver for ESP8266, ESP32 (S2,
S3, C2, C3, C5, C6), and Raspberry Pi Pico W (RP2040, RP2350). It was

satdx62 06/16/2026 10:28 PM
Currently, HyperSerial, HyperSerialWLED, and HyperSerialPico are
available. For HyperSerial and HyperSerialWLED, ESP32 models with a
serial port chip that supports a speed of 2 Mb are recommended in order
to use the AWA protocol with data integrity checking at a speed of
2,000,000 baud for use with HyperHDR. Please note that for ESP32 models
with CH340/341 and CH9102x serial port chips, you must install (or
compile yourself, if necessary) a kernel driver dedicated to your webOS
version. The only ESP model that does not require a dedicated kernel
driver is the ESP32-S2 Mini, which supports speeds of up to 5,000,000
baud. HyperSerialPico is flashed onto the RP2040 Pico, which is
currently the most powerful hardware available and also does not require
a specific kernel driver to operate. We recommend using a board with an
integrated level shifter, such as the Adafruit Feather RP2040 Scorpio,
the Pimoroni Plasma 2040, or the more affordable ItsyBitsy RP2040. The
Adafruit Feather RP2040 Scorpio and the Pimoroni Plasma 2040 have
multiple DATA outputs, which allows the use of two segment displays to
drive more than 300 LEDs without delay (low-latency performance). With
the ItsyBitsy RP2040, you can use a single-segment solution for up to
300 LEDs. (edited)

The GLEDOPTO GL-C-016WL-D does not use a separate chip (such as the
CP210x or CH340) for USB-to-UART conversion. Serial communication for
flashing or debugging (UART) takes place directly via the USB-C
interface of the integrated ESP32, just like with the ESP32 S2 Mini.
Therefore, no special kernel-drivers are required for webOS! For this
reason, I believe it is possible to install HyperSerial or HyperSerial
WLED for the ESP32. If you don’t need all of the WLED features, it makes
sense to flash a pure HyperSerial firmware (adalight). Alternatively,
you can try the Hyperk firmware from the same developer, which has been
specifically optimized for HyperHDR. Even though it also communicates
via Wi-Fi, it is significantly more stable and effective than WLED
itself due to the optimization. I have already received feedback from

satdx62 04/20/2026 6:01 PM
Hello, Unfortunately, both the “HyperHDR” and “Hyperion.NG” daemons, as
well as the LG's USB ports, become inactive after the device is turned
off. Therefore, there is no way to control a Hyperion instance (static
backlight) on the RP2040 via HyperSerial/Pico while the device is in
standby mode. However, that doesn’t mean there are no other options. If
you absolutely must use HyperSerial/Pico with the RP2040 and
HyperHDR/Hyperion.NG, you can implement a relatively inexpensive
solution that uses an additional ESP-8266/32 and a small electronic
circuit with a relay. If the LG is in standby mode, the relay switches
the DATA and GND lines for the RP2040 LEDs to an ESP (fallback) on which
the WLED is installed. From that point on, the entire backlight can be
controlled via the WLED app or the HA-JSON API. If that seems too
complicated, you can use a HyperSerial-WLED controller on an ESP instead
of a HyperSerialPico on an RP2040 from the start. Another option is to
host HyperHDR/Hyperion.NG on a Raspberry Pi and redirect PicCap Capture
to its IP address. This allows you to control Hyperion instances via the
app or the HA-JSON API as well, regardless of the LG’s on/off status.
So, as you can see, there’s something for everyone that can be put into
practice. (edited)

satdx62 04/04/2026 8:30 PM
The technical specifications of the HD108 RGB LED sound very good in
theory. It achieves a data transfer rate of 40 MHz. However, this refers
only to the communication speed. The PWM quality is around 29 kHz. In
practice, this means it is advantageous when building larger projects
with well over 300 LEDs. The data passes through the Stripe extremely
quickly, resulting in lower latency with a very large number of LEDs—300
to 900. For setups with fewer than 300 LEDs, there is no advantage due
to the transmission speed, as Hyperion typically runs at 20 to 60 FPS.
That is the actual bottleneck, not the LEDs themselves. Since the
HD108’s PWM should theoretically be around 29 kHz, there is actually
less flicker, especially during fast camera movements, as well as less
“banding” or step-like artifacts in dark scenes. However, I can’t yet
say whether this is achieved in practice, as I haven’t tested it myself.
What is certain, however, is that this was not achieved in practice with
the predecessor model HD0107, even though it had the same data rates and
PWM values. It should also be noted that two data lines (Data and CLK)
are used for transmission instead of just one. RGBW vs. RGB The
SK6812RGBW has true white, which is often more pleasant for the living
room. The HD108 typically only supports RGB. Technically speaking, it is
“more precise” and faster, but not necessarily more appealing. In my
opinion, the HD108 is worth it if you're building a high-end setup with
a lot of LEDs (300+) and extremely low latency or fast camera pans are
important for streaming. I'll be ordering one in the future and taking a
closer look at it. (edited)

satdx62 03/21/2026 11:49 AM
Hi, Regarding your first question: There’s no need to adjust the LED
layout to a 16:9 aspect ratio exactly. However, you should try not to
place the LEDs too far from the edges of the TV. Regarding your second
question: Yes, you can configure the LED layout to account for the TV
stand. I’ve created a sample configuration for you. With the “Reverse
direction” option, you can also flip the entire layout. Regarding your
third question: The USB-C port on the GLEDOPTO GL-C-016WL-D controller
is primarily intended for firmware updates. Yes, you can also flash
firmware other than WLED. For example, HyperSerial. Depending on which
serial chip is used, you may need a kernel driver for your LG. (To find
this out, for example, in Windows, go to Device Manager and check what
is listed under COM & LPT ports when you connect your GLEDOPTO
GL-C-016WL-D controller to the computer via USB-C.) To do this, you need
to know which kernel the LG firmware is based on. (Run uname -a in the
terminal) (edited)

@FPSUsername Perhaps you should also note that awawa-dev has made some
changes regarding the 12V SK6812. Quote: > I’m finalizing the PR by
adding native RGB order selection for the new 12V SK6812 directly in the
HyperHDR driver. A simple color swap in processing is no longer enough.
Since the white channel calibration calculates the W diode's output
based on a specific RGB profile, we need a strictly defined component
layout at the driver level to keep the math accurate. > > For now, the
default RGBW calibration is 0.8, 0.8, 0.8 (in the user settings for RGBW
with dithering), so it is symmetric and poses no problem for the 12V
SK6812. However, if changed to asymmetric (such as 0.8, 0.8, 0.7), it
can result in incorrect RGB channel colors if the user swaps the default
RGB order in HyperHDR. (edited)
