The grabber resolutions available for selection in PicCap's backend
result from the different division factors of common television
resolutions. These resolutions can be processed by the integrated SoCs
without creating unnecessary CPU load. You can determine CPU and memory
usage with the top command in the terminal under hyperion-webos and
hyperhdr. The FPS rate also drops if an unnecessarily high resolution is
selected. Depending on the SoC and available memory, the ideal
resolution and the quirks used may vary. Higher resolutions are not
necessary for Ambilight operation. The only exception is during the
calibration of a LUT. This process requires a minimum resolution of 1280
x 720, which is why a higher CPU load and fewer FPS are to be expected
here. (edited)

processes what Hyperion webOS (PicCap) provides it with. It has long

internal apps on newer LG devices. This can be circumvented by playing

my guide. It is correct that HyperHDR can work with different LUT tables
(templates) for different types of video content such as SDR, HDR, and
DV, provided that these LUT tables are available and the NV12 option is
enabled in PicCap. Hyperion.NG does not require LUT tables, so a single
color algorithm applies to all types of video content.

From webOS 3.5 to 5.x, PicCap and the HyperHDR/Hyperion.NG daemon should
start without any problems, obtain root privileges, and be compatible
with the autostart function. However, as I have mentioned in the past,
this depends on the root method used. With the rootmy.tv method, you get
a clean webOSbrew autostart without failsafe, so PicCap/HyperHDR or the
Hyperion daemon work as expected. On the same webOS versions/devices
that were rooted with DejaVuln, however, there is an autostart problem.
To ensure that PicCap/Hyperion works, certain tools or automations must
be applied. From version 5.x onwards, it should not matter which method
was used to obtain root privileges, and the function should always be
guaranteed. webOS 3.2–3.4, which was rooted using the MVPD method, is
therefore no exception here. However, there is no general wiki page or
procedure for this. I can imagine, though, that it will work as it
should if you downgrade to software version 05.60.20 for your UH615V
device and run rootmy.tv via the browser on your TV. This even worked on
my webOS 3.9 device.

brightness and contrast are triggered by HDR detection in the content
being played. Therefore, I tend to think that in your case, you should
either suppress HDR detection during the calibration of your TV or use a
suitable SDR calibration video in YUV420/YUV444 format so that your TV's
HDR mode is not automatically triggered during recording. The HLVG
plug-in for Photoshop is a tool for chromatic noise reduction. It
attempts to find, analyze, and remove minimal green noise and the
resulting green casts in some black or dark images.

satdx62 10/18/2025 11:41 AM
Hi, No, it is not necessary to recalibrate the LUT tables. In the new
version, a bug in the Infinite Color Engine has been fixed that affected
color reproduction when using the YUV or Hybrit Infinite interpolators.
Normally, the LEDs must switch off completely when black, depending on
how they are set in the image processing. However, since there are no
completely black scenes in practice, the LEDs glow dark gray, dark
greenish, or dark blue. If some “apparently” black scenes on your screen
have a green tint from the LEDs, then these scenes are not perfectly
black. Use the development magnifying glass or color picker in the
HyperHDR preview window of your web browser to see the actual color. As
you can see from the image, the black area should have a hexadecimal
value of #000000 (RGB value of 0, 0, 0), but it is actually hexadecimal
#161616 (RGB value of 0, 0, 9).
See:https://www.farb-tabelle.de/en/table-of-color.htm (edited)

satdx62 09/10/2025 5:42 PM
    which is stuck at 50hz and then it becomes a little slower!! Is this a limitation? or is it a bug?
This is not an bug. Unlike other LED controllers, the smoothing
frequency (if enabled) is controlled directly by the Philips Hue driver
and then forwarded to the bridge. This prevents unnecessary traffic
requests from exceeding the capacity of the LED driver. Since the
resolution here is determined by the driver rather than the PicCap, you
should select the “Sparse Processing” option under “Image Processing” in
the Hue instance. This will help you avoid processing bottlenecks and
delays. If frequency is more important to you than smoothing, you don't
need to enable this option, and the result will meet your expectations.
It is indeed frustrating when an Ambilight configuration consists of
different LED controllers and one of them lags behind. (edited)
