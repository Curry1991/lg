For LED cable connection: 1 esp32/HyperSPI (HyperSPI works only at small
distance but achieves very high speed, esp32 allows large SPI frames
recommended for very large LED setups) > 2 esp8266/HyperSPI (much
smaller SPI frames, a bit more prone to frames dropping) > 3
HyperSerialESP32 (can work at much larger distance than HyperSPI, 4Mb
speed popular CH9102x is best and at low price and the sketch can be
compiled to support that speed) >> 4 HyperSerialESP8266 (currently it is
hard to find genuine 2Mb capable chip) >>> 5 HyperSerialWLED v3 with
proper ESP32/ESP8266 (doesn't support latest AWA protocol extension for
the white channel calibration and can cause huge and hard to diagnose
lack of resources problems for ESP8266 especially if LED strip is not
optimally connected to proper pinout, WLED 0.13.1 has its own issues so
I can't update it now) (edited)

That's very popular & naive algorithm... unfortunately it brings very
poor results for RGBW sk6818. For such LEDs 1 WHITE doesn't equal 1
RED + 1 GREEN + 1 BLUE. Usually WHITE is closer to yellow which is nice
for room lighting but it's deformed for ambilight. Additionally WHITE
can be brighter/darker than white from RGB... Of course we can double
amount of white component in RGBW (white channel + mixing RGB) computed
for example as above. Then sk6812 will be much brighter than ws2812b,
but it will loose the saturation almost completely . We must be very
careful about the white channel calculation and almost each application
does its own way + sometimes allows user to calibrate it as he likes in
HyperHDR with proper LED driver. (edited)

[awawa_dev]
awawa_dev 07/16/2022 12:44 PM
I created it a long time ago, but now I don't have a 'root' and use the
Elgato HD60X instead. You should try to calibrate your own LUT (people,
please remember to provide the calibration log). There can be
differences between TVs as webos capturing has to handle many internal
video formats (such as different YUV encoding) on input and convert them
to RGB: and with this format finally the data is transferred via flat
buffers to HyperHDR... many aspects may influence the result like YUV
coefficients, YUV data range etc. Unfortunately, the HyperHDR could not
control this aspect on webos as it only gets the final RGB values, not
raw YUV format.

awawa_dev 07/16/2022 11:20 AM
If you are using HyperHDR with the default settings, you probably have
the color gamma for LED processing (Image Processing -> Color
Calibration) set to 1.5 which promotes saturation and lowers brightness
slightly. I left it for backward compatibility as people got used to
these values (colors are a bit more vibrant). But this makes the image
processing to LED strip colors is not 1: 1 mapping. If you want neutral
processing you should set the gamma to 1. But I'm not sure if this is
your case as this will slightly increase the brightness in low and
medium brightness scenes also ... maybe your LUT is not that perfect
after all? (edited)
