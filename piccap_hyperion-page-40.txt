only ESP AWA protocol for adalight has data integrity check. If the LED

out of resources. But usually it causes blinking not lower saturation.
Saturation or reddish/blueish/greenish effect almost for sure indicate
software bug.

[awawa_dev]
awawa_dev 04/10/2022 3:01 PM
> What would you recommend setting smoothing to? It really depends on
the user and its configuration. For the smoothing framerate: the higher
the better but we should not exceed LED hardware capabilities. WLED and
all of my LED projects can report the real framerate. So to test it: in
smoothing tab set 'Update frequency' to for example 100Hz or higher,
enable also 'Continues output'. Apply changes. Then in WLED info panel
read the real framerate. For example it's 62Hz. Go back to HyperHDR and
set 'Update frequency' to 60Hz as safe choice in the processing
configuration (and disable 'Continues output' because its not needed
anymore). Also recommend to enable 'Anti-flickering threshold value' and
'Anti-flickering timeout': as for me that filter was/is a game-changer.

[awawa_dev]
awawa_dev 04/10/2022 2:29 PM
From my point of view: LED device should have at least 2-3x higher
frequency than the video source. It does not have to be an exact
multiple of the grabber capturing rate but it should be higher than
that: just to give the smoothing processing a chance to work and to
produce "intermediate" frames. As for WLED / SPI/ Esp8266: I put the
warning about pinouts wherever I can (especially in my fork
HyperSerialWLED). From WLED perspective it's probably not a big issue
because most users are using WLED for setting static colors or the
animation, high framerate external ambient lighting data feeding is a
niche. And it's not a bug but rather wrong user configuration. Such
setup can be easily diagnose for the problem: set high (for
example >100Hz, sometimes problem appears on much lower frequency)
'Update frequency' and enable 'Continuous output' in the HyperHDR
smoothing. When software emulation is used at some point WLED may become
unresponsive which not happens for ESP32 (allows hardware pin remapping)
or for NON-SPI Led strip (probably because that they are limited to
800Kb anyway, much lower than SPI speed and have one output line).
Number of LEDs in the setup also affects it because the higher the
numbers is the more resources WLED needs to emulate the SPI.
