RGB LEDs also work, but the colour rendering is not as accurate as with
the RGBW LEDs. Yes, I know, unfortunately they are not so cheap, but

satdx62 09/30/2024 10:09 AM
Via JSON API, you can control almost all HyperHDR functions remotely,
for example in Home Assistant. With Copy JSON, you get the JSON
syntax: > { > “command” : ‘adjustment’, > “adjustment” : > { >
“classic_config” : false, > “brightness” : 70 > } > } With Copy link,
you get the link that you can use in an automation:
http://192.168.2.81:8090/json-rpc?request=%7B%22command%22:%22adjustment%22,%22adjustment%22:%7B%22classic_config%22:false,%22brightness%22:70%7D%7D
You can also use the Input Hook from Homebrew Channel to assign the
required functions to buttons on your remote control that you don't
need. In this example, I have reduced the brightness to 70% on red and
increased it back to 100% on green. You must put “curl” in front of the
link. Brightness 70 %: Rot ID:398 Action:Execute Command: curl
http://127.0.0.1:8090/json-rpc?request=%7B%22command%22:%22adjustment%22,%22adjustment%22:%7B%22classic_config%22:false,%22brightness%22:70%7D%7D
The 127.0.0.1 from the command is replaced with the IP address of your
TV. Brightness 100 %: Green ID:399 Action:Execute Command: curl
http://127.0.0.1:8090/json-rpc?request=%7B%22command%22:%22adjustment%22,%22adjustment%22:%7B%22classic_config%22:false,%22brightness%22:100%7D%7D
The 127.0.0.1 from the command is replaced with the IP address of your
TV. (edited)

This is what Awawa wrote regarding the exclusion of RGB encoding:
‘HyperHDR LUT could perform conversion to RGB and tone mapping in one
step because one of the tables performs these two operations in one go.
Then the conversion from RGB to YUV would be completely eliminated,
which would probably relieve the system. How much depends on the
resolution and capture frequency.’ What I noticed: there’s a slight
change in color accuracy (it’s not very pronounced, but it’s there), as
well as a significantly higher FPS that can be achieved at higher
resolutions. From what I understand, the color resolution in the format
received from webOS (PIXFMT_YUV420_SEMI_PLANAR) is half that of the
light resolution, which causes some losses during image conversion,
especially at lower resolutions. Awawa also mentioned that this could be
noticeable when using a large number of LEDs at a low source resolution…
Regarding my FPS tests, at 720p resolution, I get 60+ FPS, and at 1080p,
around 30-40. This might not be essential or important, but overall, it
seems to indicate improved performance without converting the frame to
RGB format. Additionally, changes in the flatbuffers format don’t
introduce any compatibility issues or anything like that. I added the
ability to switch the frame transmission method ‘on the fly’ in my fork,
and both methods work (i hope). So, it seems there’s no need to be
afraid of experimenting with it...) However, my changes were implemented
only for using the libvtcapture backend with the
PIXFMT_YUV420_SEMI_PLANAR format

satdx62 07/20/2024 12:35 PM
It depends on which ESP32 is equipped with which Serial Chip. This must
be specified in the description of the ordered ESP. The link describes
how to install it. You have to find out with uname -a which kernel
version is installed on your LG and download the correct kernel and copy
it to LG to /root/. With the script:
cat >/home/root/insmod_serial.sh <<'__EOF__' #!/bin/sh insmod /home/root/ch341.ko __EOF__ chmod +x /home/root/insmod_serial.sh ln -s /home/root/insmod_serial.sh /var/lib/webosbrew/init.d/10-insmod_serial
This will create a script named /home/root/insmod_serial.sh and a
symbolic link to it in /var/lib/webosbrew/init.d If you are using a
different driver, just replace ch341.ko with its filename.
